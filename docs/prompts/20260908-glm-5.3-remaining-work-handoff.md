## 3. 紧接着做 R2：构建、测试、版本交接

### 3.1 已有链路的准确入口

- `api/proto/workos/app/v1/source.proto`：公开 owner-scoped Source Create/Get。
- `schemas/workos-app-manifest-v1.schema.json`：唯一 manifest Schema，含可选 build 配置。
- `api/proto/workos/taskexecution/v1/repair.proto`：
  - `RepairExecutionService` 仅位于 Core 的 Harness mTLS listener。
  - `ResolveRepairBuildInput` 根据有效 lease 返回固定版本、源码和 build/test argv。
  - `SubmitRepairSourceCandidate` 只接收文件，不接收 owner/版本/权限/测试配置。
  - `RepairCandidateService.GetRepairSourceCandidate` 位于普通 Core 私有 listener，
    根据服务身份的 owner 读取 completed task；Gateway 不开放。
  - 返回原始构建输入、候选源码和 project/incident，用于下一段 Build/Test。
- `internal/core/orchestration/repair_sources.go`：事务、任务来源与失效检查。
- `internal/core/appregistry/application/build.go`：固定配置和候选读取/保存。
- `internal/harness/worker/worker.go`：执行前解析；提交候选并验证回执；禁止缺候选的成功终态。
- `internal/harness/adapters/genericcli/`：完整成功流和 exit 0 后才发布候选。
- `internal/reliability/application/deployment.go`：`HandleRepairCompleted` 仍返回
  `ErrDeploymentCandidateRequired`，这是尚未接通的位置，不是可以删除的保护。

源码上限：128 个文件、单文件 256 KiB、总计 512 KiB；普通文件清单，不接受 ZIP/TAR、
链接或宿主路径。摘要包含路径、字节、执行位。manifest 固定 sourceBundleId/sourceDigest、
不可变 baseImage 和 buildCommand/testCommand。候选只能换文件，不能改构建权限与配置。

`make test-repair-producer` 已证明真实 Gateway/Core/Harness/CLI/PG 链路：CLI fixture 将
示例 main.go 的 return 0 改为 return 42，原测试文件保持一致，候选重启后不变。
**这个门禁没有执行示例的测试或构建镜像。不要把“候选里有测试文件”写成“测试通过”。**
Fake provider 只添加明确的合成说明文件，也不能证明代码缺陷修复有效。

### 3.2 必须实现的下一段

先写/更新 ADR，定义 Runtime Build/Test 的任务、结果和失败契约；先改 Proto，再 generate，
再实现 producer/consumer。使用已有六进程边界：

1. Core 拥有输入、源码、版本和授权事实；Runtime 拥有实际构建/测试及资源隔离；
   Reliability 编排，不直接写 Core/Runtime 的表。
2. Runtime 从可信输入使用原版本固定的镜像和命令，不能执行候选自带的 Containerfile、
   网络配置、挂载配置或自选“总是成功”的测试命令。
3. 固定工具链镜像、关闭构建网络、禁止隐式拉取，限制 CPU/内存/PID/时间/磁盘/输出。
   逐项验证实际引擎能力；不要凭记忆假设 Podman 某 flag 存在或 rootless 必然支持某限制。
4. 构建/测试作业必须有持久幂等、有限重试、取消与重启恢复；不得只保存在 Go map 中。
5. 测试失败、构建失败、超时、进程退出失败、错误回执、输入摘要漂移均不得产生可部署版本。
6. 全部验证成功后，Core 才创建不可变候选版本，并交给 DeploymentController.Offer。
7. **现有 Registry 默认版本按 SemVer 最高版本选取。直接把候选注册成普通高版本会提前暴露。**
   必须设计候选暂存/发布状态，使未通过 canary 的候选不成为默认版本；同时允许受控的精确

必须新增真正穿过上述 producer/consumer 的门禁：成功、测试失败、构建失败、启动故障、

### 3.3 R2 还缺 Recovery 治理

目前 RepairAdmission 仍通过普通 TaskRouter，绑定项目 Provider；检查健康和候选能力，
但没有完整的 Recovery fallback 和 L3 审批/预算/配额/断路/usage 链。

- 健康且能力满足的 Project Harness 优先；不满足时按明确的 Recovery 配置选择。
- 两级均不可用，产生准确的不可用/等待人工结果和已有通知，不无限重试。
- 重放保留第一次 Provider、目标与策略快照，不随当前健康/配置漂移。
- App-principal 治理依赖 installation grant，不能伪装 App 身份来复用它。
  需要明确 Repair principal 的授权和策略语义，并复用合适的中立 port/事务能力。
- Generic CLI 尚无 hard token/cost budget、usage 和 kernel isolation，不能把能力 bool 改成
  true 或删掉预算检查来“接通 Recovery”。先实现保护，无法支持的组合明确 unavailable。
- 缺少 build 的旧 App 版本不能自动重建；当前 worker 会明确失败，不从 maintainer 字符串
  或运行镜像猜源码。若改善入队体验，必须先在 admission 拒绝并证明零副作用。

## 8. 必须反复检查：至少三轮不同角度

不要“一次 test 绿了就结束”。每轮记录发现、修复、命令和证据：

1. **实现自查**：沿真实调用链从 UI/RPC 到持久层再到真实副作用逐步追踪。核对每个按钮/能力
   是否有实现、是否能被当前身份使用、失败是否真实、有没有丢弃错误或固定成功。
   对新文件与修改文件逐项审查，不只读 diff 的标题。
2. **失败与重启检查**：先复现，再修复，再重复受影响门禁。覆盖边界、权限、并发、取消、
   超时、丢响应、重复请求、进程重启和上游不可用。检查写库/产物/事件数量，不能只测 HTTP 200。
   禁止放宽断言、skip 故障场景或关闭安全约束来让测试绿。
3. **完成前独立复核**：以最终代码重新检查原验收清单，运行完整必需检查；再次 generate 并
   确认没有生成漂移；检查 git diff --check、状态与文档；逐张查看新增视觉证据。
   找到问题就修复，并重新执行受影响检查，直到证据一致。

“反复检查”不是机械重复同一成功测试，而是不同角度核对真实行为；改动后必须再验证。
必须明确区分：已实现且端到端验证、只验证 fixture 的软件链、尚未实现、真正环境阻塞。
