# GLM-5.3 Goal 执行任务书：V2 持续开发会话与 Web 应用接续

> 用法：将本文件完整交给 GLM-5.3，在 goal 模式中连续执行。以下 B00–B10 是同一个目标的
> 工作包，按依赖顺序全部推进，不需要用户逐包派活。本文只定义下一阶段 P0、P1、P2。
> 依据：[V2 架构](../structure-v2.md) §3–4；编写时基线为 `main@09d70cc`。

## 0. 你的任务与最终结果

你是本轮实现者。请实际修改代码、运行必要检查、修复问题、更新文档并交付可使用的软件。
不能只输出分析、计划、接口骨架或另一份交接提示词。

**本轮总目标：在单 owner、单 Linux 主机、局域网环境中，让用户从 WorkOS 浏览器桌面
进入项目，通过 DeepSeek Harness 的原生持续会话修改真实项目文件、执行测试、追加要求，
并直接使用服务端应用；关闭窗口或换到另一台局域网设备后，可以继续会话和应用操作。**

GLM-5.3 是执行这份任务书的开发模型；WorkOS 本轮优先接入的仍是 **DeepSeek Harness**。
不要因此把产品 Provider 替换为 GLM，也不要实现自己的 Agent Loop。

交付后，用户应能完成以下操作：

1. 创建或选择 Project，关联已获授权的本地 Git／目录工作区，选择 DeepSeek Harness。
2. 打开 Agent 工作窗口，提出一个开发目标。Harness 读取文件、修改代码、执行真实测试。
3. 用户在同一项目的文件界面和 Terminal 中看到同一份文件，打开实际应用预览。
4. 用户追加第二条要求，Harness 在同一原生会话中继续；刷新页面后仍能恢复该会话。
5. 用户关闭应用窗口、切换项目或断开设备 A；持续应用的服务端进程按运行策略继续工作。
6. 设备 B 通过局域网进入项目，重新授权后找到原应用；明确接管后可以输入，设备 A 的
   旧控制连接不能继续影响应用。会话、文件和程序身份可以核对。
7. 用户可以分别断开界面、停止程序、重新启动程序；界面准确呈现运行状态和能力限制。

“持续会话”不等于浏览器保存聊天文本；“应用接续”不等于打开一个外观相同的新进程。
开发预览属于本轮；构建产物发布和回滚属于 P3，不得在本轮声称已完成该链路。

## 4. 已替你确定的实施选择

遵循下面默认值，减少来回设计。只有代码或官方版本验证证明不可行，才在 ADR 中写明
具体证据和替代方案；不能因“另一种架构更完整”扩范围。

### 4.1 持续会话与执行

- 一个 WorkOS 会话绑定一个 Project、Workspace revision、Provider/Profile 快照和一个
  原生会话引用。Core 拥有关联/授权，harness-host adapter 管理原生会话接入与私有状态。
- 每条被接受的执行输入关联一个既有 Task/run。会话保存多次执行关系；Task 的完成或取消
  不自动关闭会话。保留历史 Task API，不让其他 Provider 被迫伪造持续会话支持。
- 原生历史与上下文由 Harness 保存。Core 的消息/工具/进度投影仅供展示、审计和恢复定位，
  不新增第二套上下文压缩或“把所有聊天拼回 prompt”的会话实现。
- 一会话同时最多一个活动执行；第一版不并发改同一工作树。新输入用持久输入 ID 和幂等键。
  原生支持运行中 steer 时使用其真实语义；不支持时明确显示“已排队，下次执行使用”，
  按持久顺序提交，不假装当前执行已接收。排队只是输入调度，不是自研规划循环。
- 换 Provider/Profile/工作区不能悄悄改正在运行的会话。旧会话保留原绑定；显式新建并交接
  用户选择的资料，或要求先结束旧执行，具体规则在 B01 固定。
- 每次执行使用有效租约和预算。优先用“原生会话持久化 + 每执行重获凭据”的方式；若须保留
  原生进程，也必须解决租约轮换和撤销，不允许旧 API key 跨执行永久留存。
- Harness 崩溃时先对账。确认未执行的输入才可重试；结果不明的文件写/命令显示待核对，
  不因重新领取 Task 就自动再次执行。进程重启不承诺恢复已死亡的运行中命令。

### 4.2 一个真实工作区

- 首期只支持用户明确关联的本地 Git／目录，单 Project 一个活动开发工作区；保留既有
  WorkspaceRef 类型，不把 NAS/远端目录都顺带实现。
- Core 管归属与授权，Runtime 管实际目录装配和执行事实；建立明确的 workspace ID、
  revision、读写模式和受控执行环境引用。浏览器/Provider 不能自选任意宿主路径。
- 默认让 Harness 官方文件/命令工具通过其已验证的扩展点使用 Runtime 管理的同一环境。
  B00 必须确认扩展点，B01 固定调用链；必要的薄插件只做协议、授权和执行后端适配。
- 若官方工具只能本地执行，必须先证明所选受控环境、目录映射与凭据隔离可行；不能直接
  把 harness-host 整个文件系统交给 Bash。也不能为接通而把执行资源所有权搬到 Core。
- 用户文件视图、Terminal、原生应用与 Harness 指向同一受控目录中的同一文件。索引是派生
  视图；不能把四份临时副本都标上相同 project_id 来冒充共享工作区。
- 既有 App 文件 Bridge 的 32 KiB/隐藏路径/链接/etag 等规则继续适用。开发工具需要读取
  `.git` 等内容时定义 Agent/User 独立策略，不扩大普通 App 的既有授权。
- `cwd` 相同不代表文件隔离。现有进程级限制与内核隔离分别声明；所选执行策略要求的保护
  无法实际实施时，该组合返回 unavailable，不以系统 prompt 代替强制边界。

### 4.3 应用、连接和控制权

- App 是软件及配置，Workload 是实际运行实例，Surface/attachment 是设备访问关系。
  补关联和必要契约，不创建平行的 KasmWorkspace/EnvironmentService 平台。
- 有持续运行策略的应用：关闭窗口、切换项目、网络断线默认 detach，仅释放连接资源。
  用户 stop 才停程序，restart 产生新运行 generation；删除文件是另一项操作。
- 保留并说明服务端资源上限、空闲策略和过期策略；不能把连接 TTL 延长成无限保活。
  首期复用当前 30 分钟级别的会话上限作为有界默认策略，明确作用对象、到期行为及续用
  规则；验证接续必须在策略允许的存活期内。UI 能说明因策略停止的真实原因。
- 首期交互式 Native/Terminal 使用单控制端。控制授权由服务端绑定真实 device、
  attachment 和递增控制代次；新设备显式接管才改变它。旧连接的输入、排队输入、resize
  和迟到重连都要失效，不能靠前端隐藏输入框。
- 同一设备的连接续期不能夺走另一个已接管设备的控制权。到期、撤权、断开要释放 peer，
  停程序要完整回收进程组；detach 不能留下无限增长的媒体/输入 worker。
- Web App 自行负责页面状态持久化；本轮验证服务端程序与应用实际保存的内容，不承诺任意
  Web 页面的内存可以跨设备恢复。

4. 确定原生私有 session 状态存放位置、工作区装配、文件/命令实际执行位置、模型请求位置、
   租约更新与进程退出行为。画一张简单调用图，列出每条跨进程调用和数据 owner。
5. 特别检查：启用 Bash 后，命令能否继承或读取模型 key、Core 配置、数据库连接、Docker
   socket、其他项目目录。不能沿用 no-tools 时的假设。选择已有隔离/官方执行扩展点解决，
   不把原始 secret 放进工作区、工具输入或事件。
6. 早期探测 Docker/工具链、官方 runtime 下载、可用本地模型 fixture、已授权真实 Provider
   验收条件、第二台局域网设备。只记录可用性，不打印凭据、不擅自消耗未授权 API 额度。
   需要外部资源时尽早说明具体缺项，并继续本地实现。

**交付：** 新建 `docs/architecture/v2-harness-workspace-baseline.md`，记录精确版本、能力矩阵、
执行图、默认限制、复现命令和缺项；若有必要，实际完成官方 runtime/配置锁定调整。
上游资料只引用官方对应版本文档；文末来源是查找入口，不能作为版本支持证明。

**完成条件：** P1 所依赖的方法、执行边界和存储能力有可复现依据。遇到确定的上游阻塞，
只将受影响行标 blocked；继续 P2 和不依赖缺失能力的实现，不能伪造兼容协议完成 P1。

### B01 — 接受 V2 行为调整，先落契约与持久事实

**入口：** Agent/Harness/TaskExecution、Project binding、Surface/Native/PTY/Workload Proto，
相关 domain、既有 migration 和 Gateway 路由。

**动作：**

1. 新增专项 ADR，分别说明“原生持续会话与项目执行环境”“持续应用与设备接续”。
   ADR 编号取仓库当前下一号，不覆盖历史文件；明确调整 ADR-0028/0029 哪些旧生命周期。
2. 以 §4 为约束定义实体、状态转换、所有权、错误码、幂等键作用域、revision 和限额。
   至少区分 session、input、Task/run、workspace binding、Workload generation、attachment、
   control generation。不要把这些全部塞进一个无类型 JSON 字段。
3. 会话最少支持创建/列表/读取、提交后续输入、事件补收、取消当前执行、关闭会话；
   原生询问/审批支持时定义关联到具体会话/执行/请求的响应。用户/owner 身份服务端派生。
4. 应用最少支持发现已有运行实例、attach/detach、申请接管、停止和重启。指定哪些是
   Gateway 公开的受控入口，哪些只能服务端调用；不公开接受宿主 endpoint/运行身份的接口。
5. 保留旧方法原义：如旧 Close 表示 stop，新增 detach 并迁移桌面调用，不静默改为相反含义。
   明确旧会话迁移/终结规则；v1 字段号不复用，破坏性变更按仓库规则用新版本。
6. 原生上下文留给 Harness；Core 只持久化关联和有界展示投影。Runtime 拥有目录/运行实例/
   连接/控制事实。每表与 migration 唯一 owner，不允许跨 owner SQL 拼接授权。
7. Proto/Schema 先改再 `make generate`，接通生成 SDK。只有 manifest 确实缺必要表达时才改
   Schema；不再写一套同义 DTO，也不因文档叫 V2 就全量升级 RPC 为 v2。

**交付与完成条件：** ADR、契约、必要 migration/domain 和状态转换测试；对重复输入、
旧 revision、跨项目引用、未知状态都有明确行为。相关契约检查通过后再进入对应实现包。

### B02 — 建立人和 Harness 共用的真实开发工作区

**依赖：** B00 执行方案、B01 工作区契约。

**动作：**

1. 将 Core 的项目归属与 Runtime 的实际目录绑定打通；复用已有 mount 能力，新增必要的
   受控注册/查询入口。目录来源由操作员配置或已授权选择决定，不信任客户端提交的路径。
2. 给每个执行解析固定 workspace revision 和读写权限。只读目录写入失败；被解绑/归档/
   变更的工作区阻止新的旧授权操作，不把重试悄悄指向另一个目录。
3. Terminal 与 Native 开发应用在这个工作区启动。用户文件读取/编辑复用现有能力；缺少
   owner 工作区文件入口时添加最小入口，并复用 Runtime 文件 port，不冒充 App identity。
4. 使用同一临时测试仓库证明：用户写文件 → 命令读到；工具写文件 → 文件界面读到；
   Terminal 的 `pwd`/Git 状态一致。测试要核对磁盘内容与摘要，不能只查路径字符串。
5. 文件/命令输出有界；并发人工写入不能静默覆盖。沿用 etag 或在执行前核对版本；
   超限/冲突要可见。进程、文件锁和临时资源释放遵循现有实现边界。

**交付与完成条件：** 一个项目工作区从注册、授权、读写到真实命令执行可用；两个项目隔离，
只读/变更/撤销/越界路径失败准确。此包可用真实 Runtime 和确定性输入验收，暂不依赖模型。

### B03 — 接通 DeepSeek 原生会话和真实文件/命令工具

**依赖：** B00–B02。

**动作：**

1. 扩展中立 Provider port 和 DeepSeek adapter，使用 B00 验证的官方 session API。
   持久化原生会话状态，映射稳定 WorkOS session ID；单次 Task 的临时目录清理不能删它。
2. 每次执行复用 Task lease、有效凭据、取消和 deadline。重复提交/断线重发同一输入只执行
   一次；相同幂等键换内容产生冲突。同一会话活动执行的互斥要能跨 worker/重启生效。
3. 接入原生文件/命令工具到 B02 环境。真实工具读写文件并运行项目测试，输出退出码、
   工作区 revision 和有界结果；不能由 WorkOS 直接改 fixture 文件再声称 Harness 改了。
4. 支持至少两次连续输入；第二次在第一轮原生上下文上继续。按实际能力接入原生 Goals、
   Skills、Jobs：本轮目标循环只使用 Harness 原生能力，不实现通用 Goal 调度器。
   未接入的可选能力仍声明 unsupported；缺失两轮续聊/工具执行等核心能力则该包不完成。
5. 流式事件、消息终结、usage 与 Task 关联有界且去重；多次模型调用的累计 token/runtime
   预算不能继续用“一次 max_tokens”冒充整次执行上限。逐项核实并执行预算语义，
   无法强制的预算组合在 admission 明确拒绝，不直接删除保护以启用工具。
6. 恢复：页面刷新/Gateway 重启只补收事件，不再次调用模型；harness-host 重启可打开
   已完成轮次的原生会话继续。执行中崩溃核对输入/工具状态，结果不明就标待核对。
7. 一次取消终止当前执行及其受控子进程，会话历史保留以便用户后续继续；显式关闭会话
   才禁止新输入并按策略清理私有状态。凭据撤销与 lease 失效必须在实际执行链上生效。

**交付与完成条件：** 官方 runtime + 本地 API fixture 穿过真实 adapter、Core、Runtime 完成
两轮代码修改/测试与重连；本地 fixture 只模拟模型响应，不替代 Harness 或工具执行。
再按 §6 完成独立的真实模型验收；未具备条件时明确保留该证据缺口。

### B04 — 接通 Harness 调用 WorkOS 的最小授权工具集

**依赖：** B01–B03。

**动作：**

1. 在官方工具注册/插件扩展点上加薄适配，提供本轮最小操作：读取当前项目/工作区信息，
   列出/读取本项目成果，创建有界审阅成果，查询已授权应用状态，启动/附着开发预览。
   文件和命令工具复用 B03，不另写第二套 Bash 和文件工具实现。
2. 工具请求从有效 session/run/lease 派生 owner/project/权限；模型不能提交 owner 来选权限。
   复用已有 Core/Runtime 业务服务与授权 port，不冒充用户设备或已安装 App。
3. 每次执行系统操作都重新检查有效授权；固定 schema、输入/输出上限、错误映射与幂等键。

4. 询问与审批分别展示。原生请求带稳定 request ID，响应只能作用于匹配的活动执行，

5. 不支持的审批/工具能力要在 admission 或协商时明确说明。需要审批而没有可用响应路径的

**交付与完成条件：** 至少一条真实 Harness → 授权系统工具 → Core/Runtime → 事件/成果/预览
链路，覆盖撤权、跨项目引用、重复调用和迟到响应。原有 App → Agent 桥接路径回归通过。

### B05 — 将 Agent 入口做成可继续工作的会话窗口

**依赖：** B01、B03、B04；最终预览入口在 B08 联调。

**动作：**

1. 修改 UI 前复制受影响 `docs/ui/desktop-web/current/` 到本任务 before 目录。
2. 复用 Agent/SystemApps 入口和现有窗口系统，支持会话列表、新建/打开、历史消息、
   活动执行、追加输入、排队提示、取消、询问/审批、工具状态、测试结果、成果和预览入口。
3. 提交使用稳定输入 ID/幂等键；请求超时后查询/重试同一输入，不因刷新生成新执行。

4. 项目切换、窗口关闭、刷新不取消后台执行；明确“停止当前执行”和“关闭会话”的区别。

5. 会话显示实际 Provider/Workspace 和能力限制；不支持即时 steer 时显示排队状态。

### B06 — 将程序运行与设备访问拆开

**依赖：** B01；开发应用目录依赖 B02。可在缺真实模型验收时独立推进。

**动作：**

1. 复用 Runtime 的监督、Native、PTY 和 Surface 模块建立 App instance ↔ Workload ↔
   attachment 关联。Native 系统工具会话也必须有可追溯运行实例，不能只靠前端内存 lease。
2. 至少接通一个可从 WorkOS 应用入口启动的真实 remote-native 开发应用，优先使用已有
   Xvfb/xterm 工具链与 B02 工作区；给出可复现安装/启动配置，不另造镜像市场。
3. 桌面关闭/项目切换只 detach；清理当前 peer、输入订阅和令牌，保留策略允许存活的程序。
   再打开时服务端查询原实例并新建访问关系，不无条件重新 Create 一个程序。
4. 停止和重启经现有服务端授权及受监督生命周期执行。重启要产生新的 generation，旧
   attachment 失效；不能直接开放旧 scaffold StartWorkload 或信任浏览器指定的运行 ID。
5. 把 Registry 安装/卸载、grant/revision、归档、Reliability idle/restart/stop 规则逐一对齐。
   窗口关闭不立刻 idle-stop 持续应用；真正卸载/策略到期/显式 stop 仍完整回收。
6. Runtime 重启时核对真实进程：现有 Pdeathsig 导致进程死亡就持久化 failed/stopped；
   若按策略重启则记新 generation。不得仅根据旧数据库 running 行声称原进程活着。
7. 对 Web service 复用同样的运行与连接边界，现有 Web bundle/声明式应用保持各自生命周期。
   持续策略必须明确适用对象，不粗暴给所有 Surface 无限保活。

**交付与完成条件：** 真实程序关闭窗口后仍运行并保持应用状态；重开复用同一 Workload 和
generation。显式停止确实回收，重启产生新实例事实；断开连接无资源泄漏，策略仍有界。

### B07 — 单控制端接管与真实 LAN 媒体链路

**依赖：** B01、B06。

**动作：**

1. 服务端实现控制 lease/代次，绑定可信 Gateway device identity 和 attachment；只传 owner
   不能区分同一用户的两台设备。数据通道也校验该授权，不能只在信令入口检查一次。
2. 新设备先进入可连接/等待控制状态，用户明确点击接管；成功时原子替换控制代次，旧 peer
   与已排队输入失效。并发接管、重复请求、失联、过期和迟到续期都要确定收敛。
3. 保留 Native 短期授权和重新鉴权机制；凭据到期或设备撤销后旧媒体/输入在已声明的短期
   窗口内失效。页面 reload 不偷偷从别的设备抢回控制。
4. 沿用 Pion/Xvfb 先接通 LAN：提供实际可达的接口/地址、候选与端口配置，解决容器网络
   和独立浏览器的 UDP 可达性；不仅是删除 loopback filter。限制在操作员配置的 LAN 范围。
5. 信令继续经 Gateway，按需使用已有 LAN TLS/配对机制满足浏览器要求；不能通过移除认证
   或前端开跨域例外“接通”。本轮不要求公网 NAT、STUN/TURN 服务或跨网传输。
6. 维持实际画面/输入/坐标/输入速率限制和进程清理；不要退回固定截图、自增计数或客户端
   动画来替代服务端应用变化。真实错误展示 unavailable/failed。

**交付与完成条件：** 自动化证明接管后旧输入无效、新输入有效及连接资源有界；真实独立
设备证明 LAN 画面和输入链。若确需换图形后端，先用具体失败证据做 ADR，再通过已有
扩展点接入；不能在此包中同时维护两套未完成实现。

### B08 — 把持续应用、工作区与桌面串成可用入口

**依赖：** B02、B05、B06、B07。

**动作：**

1. 用户在项目里能找到当前运行应用、打开原实例、断开、接管、停止和重启；复用应用窗口/
   Dock/现有应用入口。断开、被接管、已停止、已过期状态清楚，不让用户猜按钮影响。
2. Terminal、Native 开发应用和文件界面关联 B02 工作区；用户能亲自查看 Harness 修改并
   运行测试。通过已批准的启动配置打开一个真实开发预览，记录项目/workspace/Workload。
3. 至少一种 Web service 预览通过已有代理/Surface 路径直接使用；预览从工作区运行，
   有真实响应与进程身份，不依赖 iframe 指向操作员机器的任意 URL。
4. 原生应用进入 B06/B07 的持续生命周期。设备 B 能从服务端找到它，不需要复制 A 的
   localStorage、cookie、内部 session ID 或手工访问数据库。
5. 区分“预览当前工作区”与“发布正式版本”。本轮提供前者，UI 和文档不能因此显示 P3
   的精确构建/部署验证已经通过。
6. 把用户主要链路走完整，修复相关 loading/error/empty/expired 状态，按 UI 规范采集
   本包的 before/after/current 与三尺寸关键状态。

**交付与完成条件：** 用户不依赖开发者控制台/RPC 脚本就能完成会话、文件、命令、预览和
设备接管的主要操作；程序和连接分别控制，桌面重挂载不会误启动/误停止程序。

### B09 — 执行完整验收与失败恢复，修复剩余问题

**依赖：** B00–B08 软件链路已接通。

1. 按 §6 逐行执行验收，新增必要测试入口，并运行受影响的已有回归。
2. 确定性 fixture、真实官方 Harness、真实工具进程、真实模型服务、真实独立设备分别记录。
   不把所有证据合并成一句“E2E PASS”。
3. 原生程序接续至少使用有状态的真实应用：A 输入可辨识内容/启动有界后台任务，A detach，
   B 进入后内容仍在、后台任务确实继续，身份与 generation 相同。接管后验证 A 的旧输入
   不再生效。Web 应用的服务端状态另行验证，避免把重新渲染当内存恢复。
4. 修复失败后只重跑相关测试及被新修改影响的门禁；不要反复全仓格式化、重建所有镜像或
   为刷 PASS 重跑不相关链路。最终执行一次完整 `make generate` 一致性与 `make check`。
5. 无真实模型凭据/授权或第二台设备时，把完整可运行的验收脚本、前置条件、步骤、预期
   和记录模板提交；环境证据保留 blocked。脚本不能把缺资源静默 skip 后输出 PASS。

**完成条件：** §6 必需行有通过证据；外部行仍缺失时，只能记录软件已完成和验收受阻，
不能把 P1/P2 全部标 done。继续其他可执行事项，不因一项环境条件缺失停止整批实现。

   但长期结论、可复现命令与脱敏证据必须在仓库文档/测试中，不能只留临时日志路径。
5. 核对 diff 只含本轮变更；生成变更可复现；提交到唯一任务分支，按已有授权交付。
   有外部验收阻塞时保留明确未完成行，不用本包的文档完成盖掉总目标缺口。

**最终报告只需要：** 完成的用户能力、B00–B10 状态、测试/真实环境证据、仍缺什么、

## 7. 检查与环境使用

### 7.1 先使用仓库现有入口

按改动选用，运行前读 Makefile 目标和关联脚本，避免误停共享栈：

```sh
make generate
make check
make test-deepseek-fixture
make test-deepseek-structured-review
make test-app-files
make test-terminal-sessions
make test-native-surface
make test-lan-pairing
```

以上不是要求每包都跑一遍。单包先跑相关单元/集成测试，契约生成后检查差异，最终统一收口。
新增本轮组合门禁时，优先新增清晰的 Make 入口，例如 `test-harness-sessions`、
`test-workspace-execution`、`test-surface-continuity`、`test-v2-development-journey`。
这些是**本轮待新增的建议名称，当前不保证存在**；先实现脚本与测试，再报告命令通过。
真实模型和 LAN 设备验收分别设独立入口，明确前置条件，不能被本地 fixture 自动标通过。

功能任务仍遵循 AGENTS.md 的测试和 UI 证据要求。前一次“只改架构文档不验证”的指示针对
那次文档交付，不能自行推导为本轮功能开发免验收；用户对本轮另有明确要求时以其为准，
但未运行的检查始终不得记为 PASS。

### 7.2 主机缺工具时

编写任务书时主机有 Docker，曾缺少 make/node/pnpm/go；执行时先检查，不假设环境未变。
Makefile 已提供 Go/Node/Buf/SQLC 容器，不重复安装整套宿主工具链。

若仅宿主缺 make，且当前 Docker CLI、socket 和 Go 镜像可用，可以用已有模式运行：

```sh
docker run --rm --user "$(id -u):$(id -g)" \
  --group-add "$(stat -c %g /var/run/docker.sock)" \
  -v "$PWD:$PWD" -w "$PWD" \
  -v /usr/bin/docker:/usr/local/bin/docker:ro \
  -v /var/run/docker.sock:/var/run/docker.sock \
  golang:1.26.7-bookworm make generate
```

这是**开发检查容器**的入口，不是产品应用/Harness 工具的运行配置；不得把 Docker socket
挂给用户应用或模型命令来省略 Runtime。镜像版本取执行时 Makefile，Docker CLI 路径实际确认。
同路径挂载让内层 Docker 能找到仓库；不要额外启动 Docker-in-Docker。

运行可能改文件的 generate/format 前确认任务分支。只格式化改动文件，不用全仓格式化制造
无关 diff。按任务使用独立 Compose project/临时数据库；不 `down -v` 清共享数据，
不终止非本任务容器。长命令保存退出码和脱敏日志，失败先读取日志再决定修复动作。

需要的最小外部条件、恢复后的下一条动作。所有可独立完成的软件工作做完之后，才可以因
剩余外部条件交付“实现已收口，验收受阻”；不得把总任务改成 done，也不能只交一份计划。
