## 0. 任务、结果和停止条件

你是本轮**实现者**。实际修改代码、协议和迁移，执行检查，修复失败，留下可复现证据。
不能只写分析、接口骨架、另一份提示词，不能靠更新状态文字把功能标成完成。

本轮交付 **P3 的小型单机 App 发布链**：从当前已有的不可变源码包和固定 build/test 配方，
运行真实构建与测试，保存有摘要的不可变**应用发布包**；Core 将发布包绑定到不可变
候选版本；Runtime 使用该包启动真正的正式 App Workload；Reliability 根据实际运行状态
完成 canary、发布或回滚；用户重新打开 App 时看到对应版本的真实服务行为。

一条最低限度的贯穿演示必须成立：

1. 有一个已安装、可经正式 `Surface` 打开的旧版 Web Service App，HTTP 行为为 A。
   旧版发布包可以由受限的本地管理员导入；导入必须真实落盘并验证，不能只是测试表行。
2. 一条真实修复任务产生候选源码；既有 Runtime Build/Test 执行固定命令，生成行为为 B
   的发布包。旧版 A 和新版 B 由**独立于候选源码**的 HTTP 断言区分。
3. 候选 manifest 精确引用 B 的发布包。Runtime 在 canary 启动时证明运行的是 B 的包，
   通过实际 HTTP 健康/行为观测后才发布。关闭浏览器窗口、重新进入仍得到 B。
4. 故意制造 B 启动失败或 canary 故障，Reliability 回滚到旧版本；新的正式 Workload
   确实使用旧发布包并返回 A。已有 owner 手动版本回滚也必须恢复 A。
5. 构建失败、测试失败、包丢失/损坏、用户中途换版本、重启及请求重放均不误发布或
   启动旧包冒充新版。用户界面和能力状态如实显示等待、失败、回滚或 unavailable。

**全目标完成的判据**是：真实进程和 HTTP 响应证明 A→B→A，源码摘要、构建作业、
发布包摘要、候选 manifest、安装 pin、Workload generation 和 canary/回滚记录可串联；
最后执行 `make generate` 后无新增生成差异、`make check` 通过，并保存规定的 UI 证据。
只看到 `build succeeded`、安装版本号变化、Surface ID 变化或 fixture engine 的健康成功，
都不是这个判据。任一必需项缺证据时，保持该项 blocked/scaffolded，不宣称 P3 完成。

## 2. 固定范围和进程归属

### 本轮包含

- Runtime 保存、验证、读取有界不可变发布包，建立真实构建输出与包的关系。
- Core 的 staged/published 版本保存、重验发布包身份；源包、构建包和 manifest 都可追溯。
- Runtime 的正式 App Workload 能启动精确 `base image + release bundle`，并通过 Surface
  提供旧版和新版的真实 HTTP 行为；容器资源/隔离能力如实声明。
- Reliability 只凭精确候选、实际 Workload/Surface/健康事实决定 canary、发布、回滚。
- 用户至少能看到版本、发布状态、失败原因类别及明确回滚动作。必要的最小 UI 改动要验收。
- 兼容旧 `web-bundle`、已有容器 manifest、项目开发预览、旧 Task/App→Agent 与 owner
  手动版本切换；新发布能力不能意外扩大 App grant 或凭据能力。

### 本轮不包含

不做 P4 的公网/TURN、两设备 A16 补验、移动原生、镜像市场、多主机存储/调度、任意
Dockerfile/镜像构建平台、任意 Git 仓库一键发布、数据库自动迁移和更多 Provider 深度接入。
不要求 DeepSeek 自己发现修复目标：以现有 Repair task + Generic CLI 确定性候选做正式
发布 E2E 即可；这证明交付链，不宣称真实模型自动修复质量。不得用仓库中的 fake Workload
engine 代替正式运行验收。P1 的 Docker 开发预览仍是开发工具，不变成 App Registry 的发布。

六进程边界仍为 gateway、core、harness-host、runtime-host、reliability-host、indexer。
Core 持有注册版本和安装授权；Runtime 持有构建作业、发布包字节、容器和 Workload 事实；
Reliability 持有监督与部署编排。只用版本化 RPC、port 和事件跨进程，禁止跨模块 SQL 或
共享可变 entity。Domain 不导入 SQL、HTTP、Docker/Podman 或其他 adapter。新 migration
按表 owner 分别建立，既有迁移只向前追加，不编辑已应用历史。外部写有幂等键/etag，
时间 UTC、资源 ID UUIDv7，事件消费者持久 cursor 且能重复消费。

## 3. 本轮默认实施方案：固定镜像 + 不可变应用包

采用 **`app-bundle.v1` 发布包**，不在这一阶段建设 OCI registry。含义如下：

```text
Core: 原始 manifest + 不可变源码包 + 固定 build/test/output 配方
  → Runtime: 在隔离环境内构建、测试、收集 output 目录
  → Runtime: 发布包以内容摘要保存为 ready，不再指向临时构建目录
  → Core: staged manifest 绑定精确 artifact_id + digest
  → Runtime: 用固定 digest 的基础镜像，挂载精确发布包到 /app（只读）
  → Reliability: 运行 B、观察、发布；或启动旧包恢复 A
```

`runtime.image` 仍表示固定、已在本机准备的不可变执行基础镜像；它不代表应用的新代码。
新版本必须另外绑定 `runtime.artifact`（名称可在 C01 ADR 中精确冻结），正式启动时
核对基础镜像身份、发布包摘要、runtime.command 的目标文件与 Workload 实际 mount。
只要包不同且实际程序从只读 `/app` 执行，同一基础镜像可以承载不同应用版本。旧的
无 artifact 的容器 manifest 继续走原既有路径；不能静默替它补一个空包。若 B 能改变
旧镜像里程序的隐藏路径，但 `/app` 的 B 并未被执行，该验收必须失败。

先以 versioned JSON Schema 固定一个最小 `build.output` 配方：格式必须是
`app-bundle.v1`，输出目录为规范化相对路径（例如 `dist`），不可由候选、浏览器或
模型运行时改写；`runtime.artifact` 是部署事实，只有可信 Runtime 完成的 ready 包或
本地管理员受控导入的旧版 ready 包可以填入。面向用户的 manifest 仍只用现有版本化
Schema；Go 只能从已验证 canonical manifest 投影执行字段，不得再手写一套同义 DTO。
字段名、扩展点和向后兼容细节在 C01 ADR 中冻结，先改 Schema/Proto 再改消费者。

### 3.1 发布包的不可变性

- 输入沿用源码包的路径/类型上限。输出仅允许普通文件和必要目录；拒绝 symlink、hardlink、
  特殊文件、设备、socket、绝对路径、`..`、重复/冲突路径、跨挂载与超限条目。
- 采用一个**版本化的确定性字节编码**（可用受限规范 tar）：路径排序、固定所有者/时间、
  固定权限规则，摘要计算覆盖完整包字节。解包前后都重算并比较摘要；不得以目录名、
  数据库字段或用户声明的 SHA 代替实测。标明内容摘要与 manifest 摘要的不同含义。
- 默认上限：单文件 32 MiB、整包 128 MiB、最多 1024 个普通文件、单 owner 暂存与 ready
  包总量 2 GiB；具体数字若必须调整，先在 ADR 中给实际可复现的资源证据与测试。
  成功/失败都要限制临时构建目录写入，不能仅在事后压缩时检查大小。到上限 fail closed。
- 只读包仓库由 Runtime 拥有，0700 私有根，原子写入 `tmp → fsync → rename → dir fsync`，
  完整元数据和 ready 状态由 Runtime 表记录；跨文件系统/DB 提交窗口需可对账。
  只能通过受控 descriptor 打开，禁止跟随仓库中的链接或按外来路径访问。
- 先只清理未被 ready 或版本引用的 job 私有临时文件；**不做自动删除 ready 包**。
  这避免 Core 与 Runtime 没有分布式事务时误删已发布包。容量到顶时明确拒绝新构建，
  不删除旧版本。后续 GC 是独立任务。
- `ready` 的前提是构建和测试都成功、输出被完整冻结、digest 校验通过，且作业的有效
  lease/代次仍然拥有提交权。取消、超时、重试输家和崩溃中的半包绝不能变成 ready。
  重试同一 task/job 重放首个合法结果；同键不同输入稳定冲突。

### 3.2 正式运行与能力声明

Runtime 专用 Docker 后端是本轮在当前宿主上可实现的默认正式 App runner。它属于
runtime-host 的受监督 adapter，使用 server 派生的安装身份与启动描述；不暴露旧
`StartWorkload(WorkloadIdentity)` scaffold，不把 Docker socket、宿主凭据或额外挂载
传给 App。程序容器只得到所需 `/app` 发布包只读挂载、固定内部网络与有限 tmpfs。
默认禁外部网络和隐式拉取，基础镜像必须事先按真实 digest 准备；不得接受 tag、伪造的
digest 或 `latest`。检查 container ID、image ID、mount 源、只读属性、argv、端口、
限制、owner/app/version/artifact labels 与 Core 当前 pin，然后才报告 running。

现有 Podman/rootless profile 和假引擎保留各自能力事实。Docker profile **不得声称
rootless**。CPU/memory.max/pids/wall-clock/网络/只读挂载等保护需要从实际容器和内核
读回验证；旧 profile 要求的 `memory.high` 等若无法由该后端实施，不得映射成别的
保护然后宣布等价。C00 原型必须写出逐项支持矩阵；C01 为新 profile 明确所需保护，
任何必需保护缺失时该部署返回 unavailable，不降级到宿主进程运行。可以在 ADR 中把
未支持的软高水位标为独立 unavailable 能力，但不能默默改变旧 profile 的保证。

工作区 Docker 程序与正式 App 容器使用不同的 purpose/namespace。Runtime 重启时
只能按完整受信标签对账其拥有的容器：开发工作区原来的清理规则不能误删正式 App；
正式 Workload 的恢复/终结按其持久事实和真实容器决定。不得用前端 session 是否存在
来判断程序是否正在运行。停止、重启与版本切换必须产生新的 generation；旧 Surface、
控制 token 和后台输入不能操作新 generation。

### 3.3 发布裁决

1. Reliability 从 Core 读取已完成 Repair task 的原输入和候选源，提交 Runtime Build/Test。
   候选只能变更文件内容；base image、build/test/output 配方及运行权限来自原 manifest。
2. Runtime 返回 job 与 ready 包 `artifact_id/digest` 和来源摘要。Core 私有注册时**重新
   向 Runtime 查询** job 与包的权威事实，核对 task、owner、app、原 manifest、候选源、
   固定配方、输出格式与 ready 状态；不能只信 Reliability 请求中的 ID/digest 字符串。
3. Core 派生 staged manifest，写入新 `runtime.artifact`，保留已经授权的 command、port、
   resources、health、permissions 和基础镜像，不改变用户安装 pin。任何两次调用必须
   重放同一个版本与完整摘要；失配返回冲突/损坏，不追加第二版本。
4. `TransitionCandidateVersion` 仍用预期 project revision 做 CAS；用户在构建中或
   canary 中主动换版本时，不再覆盖用户选择。Reliability 的 ledger 在副作用前持久记录
   artifact 身份和旧版本 pin。StartSurface 必须等 Runtime 核实新 Workload 的实际
   artifact/generation，健康探针过关后才进入可观察 canary；一张 Surface 票据不够。
5. Canary 期间有新 incident/启动失败/包不可用时走已有有界 rollback；回滚不仅切回
   Core 版本，还要停止或隔离失败 B，启动/核对旧包 A 的新 generation，并再次读到 A。
   未核对成功只能标记 rollback pending/failed，不能显示 rolled_back。
6. Canary 通过后 `Publish` 才使 staged 版本 owner 可见。重复消息、调用超时、重启、
   丢确认要依据持久台账和精确产物收敛，绝不因幂等重放把后来用户的版本选择覆盖回 B。

### 3.4 旧版首次导入与人工路径

为演示真实 A→B→A，提供最小**本地管理员发布包导入**路径：管理员将按同一包格式
准备的旧应用包，经已认证的 Runtime admin Unix socket/本地 CLI 导入；Runtime 同样
执行上限、解包、摘要、路径和 ready 校验，并记录 `origin=operator_import`。
该来源可以绑定到一个初始 App 版本，但**不带“已通过本轮 Build/Test”的证明**；UI/API
显示来源。接口不进 Gateway，不接受浏览器提交宿主路径，不允许任意系统目录/secret
导入。Core 在注册初始版本时必须从 Runtime 查询 owner/app 与 ready 身份；版本创建
仍受现有 Registry 授权、manifest 校验与幂等约束。

对旧版已有 image-only 安装，保持既有运行语义；首次转为 bundle profile 要由明确的
新版本/安装操作完成，不在读取旧版本时自动变更其 manifest。若最低 A→B→A 场景可
用已受控导入且真实运行的旧 bundle 完成，就不扩建一般用户用的“上传任意包”界面。

   任一必需项与描述不符，停止该容器并返回失败。

### C06 — Reliability 用运行事实完成发布与回滚

**依赖：** C04、C05。**入口：** `internal/reliability/application/{buildtest,deployment,repair}.go`、
`internal/reliability/transport/deployment.go`、台账 adapter 和既有 fault matrix。

1. `BuildCoordinator` 从 Runtime 的权威 Build/Test 查询取得 ready 包身份，核对 job/
   source，再向 Core 注册；把包身份和新旧版本精确快照存入 Reliability 自己的 ledger。
   不能因为 `GetBuildTest.state=succeeded` 就假定有包，也不能从候选源码再构建一个
   未验证的新包。
2. `StartSurface` 的成功判定须包含：Core 安装 pin 等于候选版本+manifest digest；
   Runtime 有一个实际 running 的 Workload，其 image/artifact/generation 与候选精确匹配；
   Surface 绑定该 generation；健康端点真实返回通过。读到 pending/unknown/失联时保持
   待观察或失败，不转 canary。多个组件观测非同一时刻时，复核 pin 与 generation，
   避免用户改版和 workload 重启之间的拼接快照。
3. Canary 期间持续检查同一候选代次和实际健康；有 scoped incident、进程死亡、包丢失、
   身份漂移或用户主动改版时，按已有明确的优先级停止自动推广。用户主动改版不得
   被自动 rollback 覆盖；给出 superseded/abandoned 之类终态与准确事实。
4. 自动 rollback 先用已有 Core 精确 previous pin/CAS；然后终结或隔离失败包的实际
   容器，启动旧 version+artifact 的新 generation，重建/核对 Surface 并读到旧服务
   的健康/行为。只有这一步成功才能记 `rolled_back`；Core pin 回去但旧程序没起来
   时保留 pending/failed 和可重试动作。重复回滚和丢响应不再额外回滚到更旧版本。
5. Promote 前再次核对 pin、artifact、健康和观察窗口，才调用 Core staged Publish。
   Publish 结果丢失时按同 task/manifest 查重放，不重复建版本；已经由用户切离的
   installation 不得被重新抢占。保留现有失败最多次数、候选串行和 Incident 作用域。

**完成条件：** 成功发布有真实 B 行为；失败回滚有真实 A 行为。仅 ledger/state
转换或 fixture Surface 成功不满足本包。

### C08 — 崩溃窗口、权限和回归矩阵

**依赖：** C02–C07。**目标：** 把成功路径以外的可预期风险收敛成稳定结果。

逐项构造并保留测试/记录，至少覆盖：

| 时机 | 需证明的结果 |
| --- | --- |
| Build 运行中进程死亡；worker 租约换手 | 同一作业至多一个 ready 包，旧 worker 晚到不可覆写；未知副作用不随意重放 |
| 已写包未写 DB；已写 ready 未回包 | 重启按真实 digest 收敛，同 key 重试不产生不同包或失踪成功 |
| 构建成功、测试失败；测试成功、输出缺失/超限 | 没有 ready 包、staged 版本或部署副作用 |
| 包文件被删除/篡改、基础镜像缺失 | 启动明确失败；不重新下载、从源码重编或运行旧镜像应用代替候选 |
| 导入畸形包、link/路径逃逸、跨 owner 引用 | 完整拒绝，不能读写包库外的文件或复用他人包 |
| Core 在注册前/后或 Runtime 在启动前/后重启 | 版本和容器身份可对账，不出现“双成功”或虚假 running |
| 同一 installation 两次 Offer、两个并发 canary | 只有一个精确 pin 与一个有效候选；另一个延迟/拒绝，不互相回滚 |
| 用户升级/回滚、卸载、项目归档、撤 grant | 自动流程停止覆盖用户选择；不借重试恢复已撤授权 |
| B 启动故障、canary 新 incident、回滚旧包也缺失 | 终态如实；旧包不可用时不能把 Core pin 变更显示成已恢复 |
| 程序重启、旧 stop/Surface 回执晚到 | generation 增长，旧控制与旧前端状态不影响新 Workload |
| 资源/网络/镜像/挂载保护不满足 | profile unavailable，绝不转无隔离宿主执行或采用 fake engine |

安全回归还要复跑 App grant、Task 租约、Workspace Docker、Web Bundle 和旧版
owner 手动回滚的相关门禁，确保新 bundle mount 不是普通 App 的文件 Bridge，也不
把模型凭据放入 App/container/env/log。公共 RPC 的超大请求、重复 key 与越权访问
照现有净化错误语义处理。

**完成条件：** 矩阵测试含真实 PostgreSQL/Runtime/容器的关键窗口，不靠只测
mock 状态机；任务记录链接每类结果。无法在本宿主触发的环境特定项写准确条件与
可复现门禁，不能伪造 PASS。

### C09 — 隔离六进程、真实服务行为的 P3 门禁

**依赖：** C00–C08。建议新增 `make test-v2-p3-delivery`（实际名称由任务记录固定）。
旧 `make test-repair-buildtest` 继续作为回归，不能代替新门禁。

1. 门禁建立**自己的**数据库、owner、项目、artifact 目录、容器 namespace、端口和
   无秘密 fixture；包含 Gateway、Core、Harness、Runtime、Reliability、Indexer 六个
   产品进程及真实 PostgreSQL。不会重置共享开发栈。模型响应使用确定性 Generic CLI
   或本地 fixture；不要消耗 DeepSeek 费用。第三方基础镜像先以固定真实 digest
   预备，测试中的 build/launch 都必须 `pull=never`；需要预置镜像时写明可复现步骤。
2. 通过 Runtime 本地 admin 导入真实旧 A 包，Core 注册、安装并经正式 Surface 打开。
   从用户可访问的受限 HTTP/浏览器入口读到 A；记录版本、包 digest、Workload ID/
   generation、engine inspect 的镜像和只读挂载证据。不能直接手动插入“成功”
   artifact 表行。若人工模拟 Incident 的测试独立存在，主贯穿门禁仍须从真实
   Workload 故障或可靠的监督触发一路进入 repair ledger，不在数据库插入最终状态。
3. 真实候选将受控源文件从 A 改为 B，运行现有固定 build/test；测试用例本身是
   fixture 的可信输入，不能由候选覆写。独立 HTTP oracle 在候选外，明确 A ≠ B。
   通过真实 Core/Runtime/Reliability 的私有 RPC 完成 staged→canary→published；
   经同一公开 Surface/HTTP 再读到 B，并核对新包/新 generation。
4. 在另一独立测试项目或重新建立的 fixture 触发 B 的启动失败/canary 故障，验证
   Core pin、Runtime 容器、Surface 响应和 Reliability ledger 都回到 A。再验证
   owner 手动 rollback 的 A 行为。至少一次中途重启 Runtime、Core、Reliability
   后重放相同键，证明没有跨进程猜测成功。
5. Chromium E2E 通过用户可见窗口确认版本状态、进入实际 App、回滚结果；固定
   fixture 的视觉证据由 C07 管理。若没有第二台设备，P3 门禁只验本机浏览器；
   A16 仍 blocked，不拿两个浏览器 context 当物理 LAN 验收。
6. 清理仅本门禁创建的容器、DB、包目录、临时 key/证书和端口。失败时保留**脱敏**
   诊断路径；不得自动 prune 共享镜像、volume 或宿主用户工作区。记录完整命令、
   各阶段日志摘要、代码/包/manifest digest 与 HTTP A/B/A 响应。日志不保存源码全文、
   Provider 凭据或外部用户数据。

**完成条件：** 测试真正看到正式 App 的 A→B→A 和对应产物身份；旧 gate 与新 gate
区分记录。任何真实容器能力缺失使本项 blocked，并在 status 中保持诚实能力级别。

## 7. 特别防错：碰到这些情况应先停下查实

1. **只改 `runtime.image` 字符串或 `version`，没有真实新包。** 即使 install/surface
   测试全绿也不满足 P3。必须读到 B，且运行对象 digest 能与 Build/Test 包相等。
2. **把构建目录/宿主工作区当发布包。** 临时目录会删，工作区可变；必须复制/冻结到
   Runtime 管理的不可变存储，并在重启和原目录删除后仍可启动。
3. **把 `fake-fixture`、项目预览或开发 Docker 容器当 App Workload。** 它们能证明
   软件流程的一部分，不能证明正式安装的 App 版本和 Service Surface 跑了新内容。
4. **只验证源码/包摘要，不验证实际容器。** 必须以 inspect、只读 mount、Workload
   generation 和 HTTP 响应连接，缺任何一环不宣称“已部署”。
5. **Reliability 仅比较 SemVer。** 发布和回滚的旧/新对象是完整 manifest、image、
   artifact、command、resource policy 的快照；防止同版本不同内容、用户中途换版。
6. **测试候选自己提供或修改的断言。** 可信固定测试与独立 HTTP oracle 留在门禁侧，
   候选只提议代码内容。不要用候选写一个 always-pass 测试证明修复质量。
7. **给 Docker 标 rootless 或把软件观察当内核隔离。** 能力以现场实测为准，不可用
   的保护返回 unavailable。旧 Podman profile 的 rootless 语义不能被悄悄降低。
8. **隐式拉取镜像或删除共享资源。** 构建和启动都需要预置固定 digest；清理只限本
   任务明确创建并带完整标签的资源。不要因门禁失败清空用户 Docker 或数据库。
9. **从模型付费服务获取“更真实”的 P3 结果。** 交付系统的真实含义是构建/运行/
   HTTP/回滚真实；候选可以确定性生成。上轮 DeepSeek 真模型两轮已验收，重跑须有
   本轮明确的费用授权，本任务不需要。
10. **把状态写得比证据高。** 无真实正式容器或无 A→B→A 时，任务保持未完成，
    `status.json` 最多写已经实测的部分能力；P2 A16 和 P4 仍是单独事项。
